# 原始像素输入与渲染方案（待开发）

2026-11-08 登记。本文是后续开发要求，不是已存在的文件格式、UI、CLI 或 API。涵盖无文件头的 RGB、灰度、YUV、Bayer 数据；相机 RAW／DNG 作为带元数据的文件格式在 [格式待开发清单](FORMAT_ROADMAP.md) 中另列。

## 必要信息与入口

规划专门的“原始像素打开／参数设置”入口。扩展名和文件长度不足以唯一确定布局，不能按 `.raw` 或 `.yuv` 自动认定格式。未提供的参数必须请求补充，或使用明确展示、可修改并保存的默认配置，不能静默猜测。

| 参数 | 规划要求 |
| --- | --- |
| 宽、高 | 有效图像尺寸，以像素为单位，与含 padding 的存储行长分开 |
| 像素格式 | 具体格式及通道顺序；YUV420／YUV444 只说明采样方式，不能代替存储布局 |
| 有效位深与存储单元 | 区分 10 位有效数据与 16 位存储，区分整数、半浮点与浮点；非 8 位单元声明有效位对齐方式 |
| 字节序／打包 | 适用时指定 little／big endian、有效位位于高位或低位、逐组打包规则 |
| 数据起点 | 文件头／前缀跳过字节数；不得假定图像从第零字节开始 |
| 平面布局 | 各平面的顺序、相对数据起点的偏移、行跨度；UV／VU 不能混用 |
| 图像方向 | 存储行方向及明确的翻转／旋转设置，与像素格式独立 |
| 颜色解释 | RGB／灰度的传递函数、色域或明确的未校准预览模式；YUV 和 Bayer 的额外参数见下文 |
| 多帧扩展 | 多帧原始文件后续另设帧跨度、起始帧／帧数、帧率；单帧文件不自动当作动画 |

规划将参数保存为独立描述配置以便复用，导入时保留所有会影响显示和性能的选项。配置格式和具体产品交互留待实现确定。

## RGB 与灰度待开发项

- [ ] RGB24、BGR24、RGBA8、BGRA8；显式说明 alpha 语义和通道顺序。
- [ ] RGB565，固定并记录通道掩码和字节序。
- [ ] Gray8、Gray16，区分真实位深与存储位宽、字节序和显示映射。
- [ ] 高位深 RGB／RGBA、半浮点／浮点输入另列具体格式，不以“RGB”概括；HDR 显示按输出链路单独验收。

## YUV 待开发格式

按“色度采样 × 存储布局 × 位深／打包”分别登记，不将 4:2:0、4:2:2、4:4:4 当作可唯一解析文件的名字。

| 采样 | 布局 | 计划格式／必要区分 | 状态 |
| --- | --- | --- | --- |
| 4:2:0 | Planar | I420／IYUV（Y、U、V），YV12（Y、V、U） | 待开发 |
| 4:2:0 | Semi-planar | NV12（Y＋UV），NV21（Y＋VU） | 待开发 |
| 4:2:2 | Packed，8 位分量 | YUYV／YUY2：`Y0 U0 Y1 V0`；UYVY：`U0 Y0 V0 Y1`；YVYU：`Y0 V0 Y1 U0`；VYUY：`V0 Y0 U0 Y1` | 待开发 |
| 4:2:2 | Planar | 显式 Y、U、V 三平面及各自 stride／offset | 待开发 |
| 4:2:2 | Semi-planar | NV16（Y＋UV），NV61（Y＋VU） | 待开发 |
| 4:4:4 | Planar | 显式 Y、U、V 三平面；每个平面均为完整宽高 | 待开发 |
| 4:4:4 | Semi-planar | NV24（Y＋UV），NV42（Y＋VU） | 待开发 |
| 4:4:4 | Packed | 按所选规范显式定义 Y／U／V 顺序，以及是否包含 alpha／填充字节；不能只写“YUV444” | 待开发 |
| 4:2:0／4:2:2／4:4:4 | 高位深 | P010／P016、10／12／16 位 planar 等按具体存储规范分项接入，逐项声明有效位、位对齐和字节序 | 待开发 |

`UYUV` 暂按用户意图中的 `UYVY` 处理，仅登记待开发别名说明；解析器不得接受一个未定义布局的名称。I420／IYUV 与 YUYV／YUY2 等别名，必须在字节布局核对后才能映射为同一格式。

YUV 设置额外包括：BT.601／BT.709／BT.2020 矩阵及适用编码规则、limited／full range、色度采样位置、色域和传递函数。不得仅凭分辨率推断矩阵，也不能把所有 10 位数据都当作 HDR。缺少信息时明确标记使用的预览假设。不能正确处理的 HDR／色度布局返回明确限制，不伪装为正确颜色。

4:2:0、4:2:2 的色度平面尺寸、奇数宽高和 packed 像素组尾部按具体规范计算；首轮若只支持对齐尺寸，必须明确拒绝不满足条件的输入，不能静默截断。

## Bayer／拜耳待开发项

- [ ] CFA 四种排列：RGGB、BGGR、GRBG、GBRG；以有效图像左上角为参照，裁剪和数据原点的奇偶变化必须同步改变 CFA 相位。
- [ ] 8／10／12／14／16 位；区分 8 位存储、16 位容器中的有效位与逐组 packed 数据。
- [ ] MIPI RAW10／RAW12、适用的 V4L2 packed 等按明确规范逐项接入；相同位深不能说明打包方式相同。RAW14 的打包规则也需独立定义。
- [ ] 配置按通道适用的黑电平、白电平、曝光／增益、白平衡增益及颜色转换；缺少相机标定时展示“未校准预览”状态。
- [ ] 先确定可复现的去马赛克算法及边界处理，再扩展质量模式。算法、白平衡、颜色矩阵、色调映射均进入配置与测试记录。
- [ ] 原始灰度／CFA 检视与去马赛克彩色显示分别验收，不能将灰度显示标记为完成 Bayer 彩色支持。

规划显示链路：`读取 → 解包／位深归一化 → 黑白电平 → CFA 重建与去马赛克 → 白平衡／颜色处理 → 显示映射 → 上传 → 绘制 → 呈现`。具体算法对处理顺序有要求时，以实现说明为准，逐阶段计时范围必须明确，不能重复计入。

## 参数校验与资源预算

- [ ] 宽高、位深、格式、plane 数量及各参数组合合法，所有尺寸／偏移／长度运算检查溢出。
- [ ] 对每个平面计算有效行字节数和行数，校验 stride 不小于有效行长；不得用 `宽×高×1.5` 概括全部 YUV 输入。
- [ ] 以 `数据起点 + 平面偏移 + (行数−1)×stride + 有效行字节数` 验证最后一次实际读取不超出文件。packed／多帧按对应规则另算，不要求最后一行必须存在未读取的 padding。
- [ ] 处理平面重叠、错误 UV 顺序、头部偏移、截断、尾部附加数据及不支持的布局，给出可定位的错误。
- [ ] 源数据、转换工作区、Bayer 去马赛克缓冲、中间高精度图、纹理及多平面纹理均纳入预算。选择 CPU 转换还是 GPU shader，不绕过内存／显存限制。
- [ ] CPU 转换路径与 GPU 转换路径单独标记和比较；格式／输出质量一致才比较性能。

## 样本与性能计划

沿用固定种子 20261108 的棋盘格随机色块：RGB 使用同源像素，YUV 必须经过记录了矩阵／范围／采样位置的转换，Bayer 必须按 CFA 采样形成 mosaic，不能把 RGB 文件改名当作原始数据。另补灰阶、饱和色、边界和已知 CFA 小图，检查布局与颜色解释；有损色度采样和去马赛克输出不要求与源 RGB 逐像素相等。

每类至少包含紧密行、带行 padding、非零文件／平面偏移、有效边界尺寸及错误参数样本。尺寸按格式能力选取普通图、4K、超大静态图；不生成“超大动图”作为验收要求。Bayer 还覆盖四种 CFA、字节序、不同打包、黑白电平、白平衡及裁剪相位。

完整测试要求见 [性能测试计划](../benchmarks/TEST_PLAN.md)：原始输入的压缩解码项填“不适用”，分别采集读取、解包、YUV 转换、Bayer 去马赛克／颜色处理、上传、CPU／GPU 绘制、呈现等待及 CPU／内存／GPU 占用。不要因无压缩解码就把总处理成本记为零。

## 布局核对依据

实现时按所选规范和版本核对格式，不将不同 API 中相似的名字视为同一布局：

- Linux V4L2 [Planar YUV formats](https://docs.kernel.org/userspace-api/media/v4l/pixfmt-yuv-planar.html) 与 [Packed YUV formats](https://docs.kernel.org/userspace-api/media/v4l/pixfmt-packed-yuv.html)。
- Linux V4L2 [Packed 10-bit Bayer](https://docs.kernel.org/userspace-api/media/v4l/pixfmt-srggb10p.html)、[Packed 12-bit Bayer](https://docs.kernel.org/userspace-api/media/v4l/pixfmt-srggb12p.html)、[16-bit Bayer](https://docs.kernel.org/userspace-api/media/v4l/pixfmt-srggb16.html)。
