# 图片加载与渲染性能待办

更新：2026-11-09。当前 review 见 [RENDERING_REVIEW-2026-11-09.md](RENDERING_REVIEW-2026-11-09.md)，具体分阶段开发及验收见 [RENDERING_PLAN.md](RENDERING_PLAN.md)。自定义 shader / RGB / YUV 直接渲染本轮**只列计划，不实现**。

## 最新需求与当前方向

2026-11-08 的“按视口请求 REGION 细节 / 懒解码”是历史方案。2026-11-09 用户进一步明确：不要先显示缩略图；原始高清画面逐行出现；加载完成后缩放和平移不能重新计算图片内容。

当前改为一次原始分辨率 NATIVE 行带解码、不可变本地 tile / LOD 缓存、按需 GPU 驻留。懒加载现在指**纹理驻留 / 缓存恢复**，不是在每次相机变化时重新扫描源图。JPEG / PNG 等顺序 codec 仍须顺序解码，progressive / interlace 仍受自身工作集限制；首行带与全图完成分别测量。

## 已落地的正确性基础

- [x] 静态图单次 NATIVE 请求，平移 / 缩放不重提 REGION 解码，不用放大 FIT 缩略图代替原始数据。
- [x] 完整原始行带就绪后提前发布 / 显示，像素不可变；背压、取消、源版本与 shutdown 契约保留。
- [x] 常驻纹理相机操作不重传；超出显存时从原始压缩 tile / 预生成 LOD 恢复，不重新解码源图。
- [x] FIT 使用共享 atlas 批量绘制；100% 对齐物理像素，保留原始细节和透明度回归。
- [x] 原始行采样 / TIFF 原生不透明拷贝路径减少无用转换；纯色缓存复用避免重复 LOD 编码。
- [x] 删除原图后继续缩放、拖动和缓存淘汰 / 恢复；非均匀 FIT、换图显存压力和 GPU 图片资源释放有回归。

这些是功能与所有权检查，不是已证明与 VS Code 相比更快。

- [x] 缩放 / 平移恢复默认在已驻留高清纹理完整覆盖范围内推进相机，不再冻结等待整个最终视口；超出覆盖仍保留最近完整画面，恢复完准确到达目标。实际像素覆盖排除屏幕外 decode halo 等待，缩放锚点、半透明和多帧移动有回归。首次原始行带显示不变；atomic 策略保留供对照测试。此优化不承诺冷区域零等待。

- [x] 交互恢复的缓存读取 / 解压移到后台：32 MiB 解压 LRU、64 项排队上限、独立 fd；过期排队项替换，完成通知唤醒 UI。
- [x] 相机工作按可见网格索引，GPU LRU / 旧画面保护按驻留集合访问，不随源图全部 tile 数线性扫描；32K 回归包含访问计数检查。
- [x] 预热一圈邻居及 FIT 的 native 中心，按空余显存和限量上传执行；热缓存小平移 / 同级缩放有零读取、零 GPU 重传断言。
- [x] 完整 tile 一次带像素创建，去除先清零、再覆盖和重复 mipmap 生成；保持局部渐进纹理的透明初始化。

## 优先性能工作

- [ ] Release 冷 / 热缓存基线：同输入、窗口、DPI、机器、WSLg / 驱动；记录实际 GL renderer，区分硬件与软件 OpenGL。
- [ ] 分段耗时与资源计数：解码 / 行带等待 / CPU LOD / 压缩 / 磁盘 / GL 上传 / draw / present；首行带、全图完成、100% 缓存就绪分别记录，交互帧 P50 / P95 / P99。
- [ ] 将**首次生成** LOD / 压缩 / 缓存写入移出 UI 线程；交互读取 / 解压已后台化。调用间上传预算不保证单次 GL 驱动调用耗时上限。
- [ ] 完善 atlas 缩小时的 LOD 质量与驻留，只使用已生成结果；不因相机操作重新生成像素。
- [ ] 把 app 索引、描述符、暂存和旧 / 新场景缓存纳入统一预算；补缓存 I/O / 磁盘不足和故障恢复测试。
- [ ] 测量 GL 状态查询、纹理绑定、相邻上传及 atlas 批处理；根据数据决定是否引入 PBO / fence。

## 已列入计划、暂不实施

- [ ] 独立 image pass / 自定义 shader，先做 RGBA8 视觉等价验证，不替换 ImGui UI shader。
- [ ] RGB8 / 灰度等原生纹理上传，正确处理 stride / alignment，保留 RGBA8 fallback。
- [ ] I420 / NV12 等多平面纹理及 shader 色度重建 / 颜色转换；明确 matrix / range / chroma siting / transfer，按布局逐项验收。
- [ ] JPEG 原生 component 输出能力评估及输出接口迁移；现有 TurboJPEG API 并未编入，不能直接假定可用。
- [ ] 可选异步上传，必须先定义完成通知、引用保留和全部资源预算，不能破坏同步上传返回即可 release 的现有契约。

## 约束

最终输出与事件交接保持引用 / 不可变语义；resident 上传借用 data / stride，不增加传输 staging 副本。大图缓存编码和 LOD 生成允许明确计入预算的工作缓冲，但不得宣传为“所有阶段零拷贝”。不以无界 RGBA 常驻、丢弃 alpha / 颜色解释或静默退回低清来掩盖性能问题。每项优化分别记录正确性、前后分段数据与内存 / 显存 / 磁盘占用。

用户原有“加载 / 放大响应不如 VS Code”的反馈仍待相同条件的专项对比；尚无此对比的量化结论。输入矩阵见 [性能测试计划](../benchmarks/TEST_PLAN.md)。
