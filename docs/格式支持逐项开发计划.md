# 图片格式逐项开发计划

本文冻结扩展格式的开发顺序、每项完成条件和提交边界。当前实际支持范围仍以[图片格式兼容表](图片格式兼容表.md)为准。

## 工作规则

每个格式都按以下顺序推进，前一步验收通过后才开始下一步。

1. 明确首版支持子集、后端版本、许可证、构建方式和资源预算。
2. 接入 Core 内容识别、解码入口、能力查询、取消、源版本检查和错误分类。
3. 添加最小真实样本或规范生成 fixture，覆盖正常、截断、损坏、异常尺寸和预算失败。
4. 接入应用目录过滤、格式名称、信息面板和必要的导航行为。
5. 完成 review、单元测试、集成测试和性能基线。
6. 更新 README、兼容表、Core 契约和开发状态，形成独立提交。

每个阶段至少保留一个可回滚的 Git 提交。一个格式的实现、测试和文档可以拆成多个提交，但不能把未验收的格式标成已支持。

## 总体顺序

| 步骤 | 格式 / 方向 | 首版范围 | 主要依赖或接口 | 验收门槛 |
| --- | --- | --- | --- | --- |
| 0 | 计划基线 | 冻结顺序、子集、提交和验收规则 | 现有 Core ABI 2 | 计划文档提交，工作区无未说明改动 |
| 1 | QOI | 无损 RGB / RGBA，NATIVE / FIT，RGBA8 输出 | 项目内 decoder，无外部依赖 | 内容识别、所有 opcode、截断 / 尾标记、尺寸 / 预算、缓存和目录测试 |
| 2 | ICO / CUR | 已完成 PNG / DIB 条目、尺寸选择、alpha / mask、CUR hotspot 校验 | 项目内容器解析，PNG / BMP 路径 | 条目选择、mask 合成、热点校验、损坏容器测试已通过；热点展示另行评估 |
| 3 | APNG | 默认图、动画 frame、blend / disposal、时长、循环 | 现有 libpng，复用动画会话 | 与参考帧逐像素比对，动画边界、循环和快速换图测试 |
| 4 | 动画 WebP | 完整画布、透明合成、时长、循环 | 现有 libwebp，复用动画会话 | 多帧合成、透明边缘、循环和取消测试 |
| 5 | TIFF 多页 | 页面枚举、选择、文件版本锚定 | 现有 LibTIFF，需 selector 设计 | 页面选择不可静默替换，源变更、页索引和首页回归测试 |
| 6 | JPEG 2000 | JP2 / 裸 J2K 静态 8-bit RGB | OpenJPEG | 有损 / 无损、两种封装、尺寸和错误分类测试 |
| 7 | AVIF | 静态 8-bit 主图，先输出 RGBA8 | libavif + dav1d | 有损 / 无损样本、透明、尺寸、取消、构建和许可证验收 |
| 8 | HEIF / HEIC | 单主图、8-bit RGBA，方向 / 裁切按样本验收 | libheif 及实际 codec | 主图选择、方向、损坏、构建和发行包验收 |
| 9 | JPEG XL | 静态 8-bit RGBA | libjxl | 有损 / 无损、透明、内容识别、构建和包体验收 |

## 独立验收轴

以下能力不能因为首版能够解码就自动视为完成，必须在对应格式的独立提交中验收。

- 高位深读取和量化策略。
- HDR 原生输出、SDR 映射和 NaN / Inf 政策。
- ICC、EXIF、方向和颜色元数据。
- REGION、随机访问、块解码和超大图工作集。
- 动画帧时长、循环、blend / disposal、seek 和应用暂停控制。
- 多页、多 part、多通道和选择身份。
- Windows / Linux 构建、静态链接、许可证、包体和干净环境运行。

## 提交命名和 review 门槛

计划基线使用 `docs: add format support development plan`。后续格式提交使用 `<format>: decoder`、`<format>: tests`、`<format>: app and docs` 三组主题，若改动很小可合并为一个格式提交。

每个格式完成前必须同时满足以下条件。

- 正常样本真实进入应用入口并显示。
- 合法但首版不支持的变体返回 `LV_ERROR_FORMAT_UNSUPPORTED`。
- 损坏 / 截断、尺寸限制、预算失败、取消和源变更分别返回对应错误。
- Core 能力查询与实际首版子集一致。
- 单元测试、集成测试和必要的性能基线通过。
- 文档没有把未验收的高位深、HDR、ICC、区域或动画能力写成已支持。
