## 2. CMake 目标与依赖边界

```text
liltview                     应用入口与组装
├── liltview_core            C23：读取、解码、任务、预读与 CPU 缓存
├── liltview_ui              C++23：ImGui、窗口与图片渲染
│   └── liltview_i18n        C++23：翻译、语言设置与格式化
├── liltview_logging         C++23：spdlog 与 C 日志回调适配
└── liltview_update          后续规划：HTTPS 更新检测，当前不创建
    └── cpp-httplib          后续首选，当前不获取或链接

liltview_core_tests          C++ 测试入口 + C23 被测对象
├── liltview_core
└── Catch2::Catch2WithMain

liltview_app_tests           翻译、版本比较等不依赖窗口的逻辑测试
└── Catch2::Catch2WithMain
```

- C 核心不链接 ImGui、spdlog、HTTP 客户端或翻译模块；所需服务通过 C 接口注入。
- 更新检测不属于图片数据预读，不能占用图片解码任务槽。
- 界面和更新模块只交换结果消息，不在网络线程操作 ImGui。
- `.c` 文件由 C 编译器按 C23 编译；使用 C++ 测试入口不改变核心编译语言。
- 对项目自身目标设置语言标准、必要特性检查和警告；不把严格警告或语言选项全局强加给第三方源码。
- 应用目标不链接 Catch2。核心可以独立构建和测试。

### 2.1 配置选项建议

| 选项 | 初始建议 | 含义 |
| --- | --- | --- |
| `BUILD_TESTING` | 开发 ON，Release preset OFF | 控制独立契约检查与测试总开关 |
| `LILTVIEW_BUILD_UNIT_TESTS` | 默认 OFF，dev preset ON | 启用 Catch2 单元测试与依赖 |
| `LILTVIEW_BUILD_APP_COMPONENTS` | 默认 OFF，dev preset ON | 启用 ImGui 目标和 spdlog 适配库 |
| `LILTVIEW_ENABLE_UPDATE_CHECK` | 后续引入，默认 OFF | 预留配置名称；当前阶段不实现启用路径 |
| C++ 标准配置 | 默认 23，兼容配置为 20 | 兼容配置需有实际构建验证，不能静默降级 |

当前阶段不获取、构建或链接为更新检测专用的 cpp-httplib / TLS 依赖，不新增检查更新入口或启动时联网行为。后续实现模块时，关闭选项仍须满足这一约束。测试关闭时不为本项目获取或构建 Catch2。

### 2.2 依赖管理约定

- 需要编译的库使用 Git submodule，纯头文件库直接提交源码，均放到 `third_party/`；保留原许可证和来源记录。
- ImGui、编译库形式的 spdlog、Catch2 声明为 submodule；由主仓库 gitlink 锁定提交，manifest 记录版本和来源。Git submodule 管理流程参考上游文档。[S1]
- CMake 只读取已准备的本地依赖，不自动下载或更新；原 SYSTEM / FETCH 模式已移除。
- ImGui、spdlog、SDL3、Catch2 四个 submodule 的 gitlink、清单与检出一致。SDL3 使用 `SDL3::SDL3-static`，不安装 SDL `.so` 或附加 SDL RPATH；系统 OpenGL、GIO、Wayland、X11、Fontconfig 仍是平台依赖。KDE appmenu 协议描述保留原 MIT 许可，构建时生成接口。最新测试和逐项验收见 [项目审查](PROJECT_REVIEW-2026-11-07.md)。
- 关闭第三方示例和不需要的功能；项目自己的测试与第三方项目的自测分别控制。
- ImGui 使用锁定版本的源码和匹配后端；可以自建 CMake target，不假定每个依赖都提供相同的安装接口。
- HTTP 客户端的 TLS、压缩等编译配置统一由一个 target 管理，避免不同编译单元配置不一致。
- 记录实际依赖树、发布包大小、运行时动态库及首次安装新增依赖；“header-only”不是体积结论。

## 3. 日志方案

### 3.1 模块分工

建议使用 spdlog 编译库形式。上游同时提供 header-only 和编译库，并推荐编译库以降低编译耗时。[S2]

C 核心只依赖日志回调，例如：

```c
typedef void (LV_CALL *lv_log_fn)(
    void *userdata,
    lv_log_level level,
    lv_request_id request_id,
    const char *utf8,
    size_t byte_count
);
```

该定义与公共头文件一致。配置阶段注册回调，文本仅在调用期间有效；userdata 必须保持有效直到核心 join 成功。

### 3.2 契约

- 回调可来自多个工作线程，应用适配器必须线程安全且不操作 UI。
- 消息仅在回调期间有效；异步保存时必须复制，不能保留借用指针。
- C++ 适配器必须在回调内部收敛异常，不让异常跨越 C ABI。
- 空回调代表关闭日志；核心不能依靠日志回调完成业务逻辑。
- 先停止核心工作，再撤销日志适配器，避免关闭时调用已释放对象。
- 按请求、错误、缓存变化等有意义的事件记录，避免逐行或逐像素日志。
- 用户可见错误采用错误码和结构化参数，由界面翻译；日志保留稳定事件名和诊断信息，不要求跟随界面语言变化。

## 4. 后续更新检测方案（当前不实现）

### 4.1 选择 cpp-httplib 作为首选的依据

当前需求是低频获取版本信息，展示是否有更新；并不需要完整的网络服务框架。

| 维度 | libhv | cpp-httplib |
| --- | --- | --- |
| 项目定位 | 事件循环及多协议网络能力 [S3] | HTTP/HTTPS 库，提供单头文件接入方式 [S4] |
| I/O 方式 | 非阻塞事件循环等能力 [S3] | 阻塞式 socket I/O [S4] |
| 本项目接入建议 | 若采用，需要管理网络循环及回调 | 独立工作任务执行请求，再投递结果 |
| HTTPS | 需要配置 TLS 支持 | 同样需要配置 TLS 后端 [S4] |
| 体积判断 | 需要裁剪后测量 | 同样需要连同 TLS 和运行时依赖测量 |

用户已确认优先采用 cpp-httplib，libhv 不再列入当前依赖计划。上表保留选型依据，不表示两种库仍待二选一。具体版本、TLS 配置和体积验证留待更新模块排期时处理，不阻塞图片浏览器主线。

该选择基于需求与架构匹配，不宣称 cpp-httplib 的最终程序一定更小或请求一定更快。

### 4.2 后续接入建议

本节在更新模块重新排期后执行，不属于当前实现范围。

- 默认禁用更新模块；只在启用后引入网络和 TLS 依赖。
- HTTP 请求在后台工作线程执行，不能放入 ImGui 每帧循环。
- 更新模块后续首轮只实现版本检查和更新说明 / 下载页面入口，不下载并替换程序。
- 使用 HTTPS，启用证书与主机名验证；TLS 后端及系统证书加载方式需要在 Linux 和 Windows 分别验证。
- 配置连接、读取等超时及整体等待策略；明确 DNS、重定向和取消的实际行为。
- 用户取消或退出时使请求标识失效，防止晚到结果覆盖当前 UI。停止标志本身不保证立即中断阻塞 I/O，须验证锁定版本的取消接口和线程退出路径。
- 限制响应大小和重定向次数；错误、离线与限流只影响更新状态，不影响看图。
- HTTP 客户端不负责 JSON 解析；版本信息来源、数据格式、解析依赖和版本比较规则另行确定。
- 关闭未使用的自动可选依赖；若选 OpenSSL，构建时要求其可用，不能悄悄构建出没有 HTTPS 的更新模块。当前上游提供 `HTTPLIB_REQUIRE_OPENSSL` 等选项，最终以锁定版本为准。[S5]
- 对比体积时统一优化级别、静态 / 动态链接方式和 TLS 后端，比较总增量；正式选择前不填写未经测量的节省比例。

## 5. Catch2 与测试分层

建议采用 Catch2 v3 系列并锁定具体版本。`Catch2::Catch2WithMain` 提供默认测试入口，`catch_discover_tests()` 用于 CTest 注册。[S6]

- 核心测试：图片大小与溢出、分档边界、解码结果、损坏输入、取消、事件顺序、缓存预算和背压。
- 接口测试：C23 对象与 C++ 测试入口的 ABI、缓冲区生命周期、错误码和关闭顺序。
- 当前应用逻辑测试：翻译完整性、回退行为和占位符；版本解析和更新状态转换随更新模块后续加入。
- 集成检查：线程唤醒、图像上传、窗口操作、字体、DPI 和 IME，不能仅以无窗口单元测试替代。
- 后续更新检测测试使用固定响应或本地测试端点，不依赖真实外网、GitHub 配额或实时发布版本；当前不为延期模块建立测试实现。
- 大图性能测试与正确性单元测试分开记录；不以某台机器上的固定耗时作为所有环境必须通过的断言。

## 6. 中英双语方案

### 6.1 范围与语言选择

- 用户已明确需要中文和英文；首版建议实现简体中文 `zh-CN` 与英文 `en-US`。
- 提供“跟随系统 / 简体中文 / English”设置，保存用户选择。
- 显式选择优先于系统语言；系统语言无法匹配时回退英文。其他中文地区标识的映射规则需要明确定义，不能宣称提供了繁体翻译。
- 支持运行时切换；由 UI 线程在帧边界应用，不重新读取当前图片。
- 当前翻译覆盖菜单、按钮、设置、提示、错误及空状态；更新状态文案随更新模块后续加入。
- 文件名、路径、图片内容和用户输入不翻译。

### 6.2 字符串管理

建议首版采用编译进程序的两份字符串表，避免仅为少量 UI 文案引入额外资源解析库。

```text
app/i18n/
├── text_id.hpp       稳定文本 ID
├── en_us.cpp         英文默认文案
├── zh_cn.cpp         简体中文文案
└── translator.cpp    语言选择、查找、回退与格式化
```

- UI 通过稳定文本 ID 获取文案，不在各个控件中散落中英条件分支。
- 缺少中文翻译时回退英文；开发检查仍应报告缺失项。
- 两种语言的格式化占位符在数量、名称和类型上保持一致；允许调整语序。
- C 核心返回错误码和结构化参数，界面选择翻译模板；可选诊断文本仅作补充。
- 单位、数字和时间的显示规则集中处理，不依赖全局 locale 改变核心解析行为。

### 6.3 控件 ID 与布局

ImGui 标签参与生成控件 ID，`###` 可以将显示文字与 ID 分开。[S7]

```cpp
// 接口示意：显示文字可变化，内部 ID 保持一致。
const char* label = use_chinese
    ? "打开图片###open_file"
    : "Open image###open_file";
ImGui::Button(label);
```

实际实现由翻译层提供显示文案，程序附加稳定 ID；翻译资源不负责修改 ID。窗口、面板和可交互列表也需使用稳定身份，切换语言不应重置选择、折叠、滚动和当前视图。

按实际文案宽度布局，验证长英文、窄窗口和高 DPI，不能只按中文长度设置固定按钮宽度。语言切换后更新文案缓存，不触发图片解码或重建图片缓存。

### 6.4 字体、UTF-8 与输入

- ImGui 接收 UTF-8 文本；使用包含所需中文字形的字体，不能把编码正确等同于字体有字。[S7][S8]
- 默认从可执行文件相邻资源目录加载未修改的 HarmonyOS Sans SC Regular，并随包保留其独立许可证；缺失时查找系统字体。Linux 使用 Fontconfig 查询，Windows 回退代码尚未实机验证。
- 缺少中文字体时给出可读提示和补救方式。仅含 UI 固定文案的字体子集不足以显示任意中文文件名。
- 评估带动态字体机制的 ImGui 版本和匹配后端。1.92 起的动态机制要求后端支持纹理更新，不能只升级 ImGui 核心而保留旧后端。[S8]
- 动态字形并不消除字体文件、字形缓存或纹理增长的成本；将冷启动和首次显示新中文字符纳入测量。
- 源文件与执行字符集统一为 UTF-8。C++20 / C++23 的 `u8` 字面量采用 `char8_t`，不能直接当作 ImGui 的 `const char*` 参数；在统一边界处理，避免散落强制转换。[S8]
- 输入法能力取决于平台后端和实际桌面环境；验证中文组合输入、候选框位置、焦点、复制粘贴及提交 / 取消行为。

### 6.5 验收清单

1. 两种语言的文本键和格式化占位符一致，回退规则可测试。
2. 切换语言无需重新打开图片，不丢失窗口与控件状态。
3. 高 DPI、窄窗口和较长英文文本不被截断或相互覆盖。
4. 中文文件名、输入与剪贴板正常；缺字和缺字体时能明确反馈。
5. UI 文案与核心错误码映射完整；核心无需翻译依赖即可运行。
6. Windows 与 Linux 平台输入、字体和字符编码分别验证，不从单一平台推断另一平台已支持。

## 7. 下一步落地顺序

1. 确认窗口 / 渲染后端和首版五类格式的解码 / 栅格化库。
2. 锁定依赖版本，建立 CMake 目标、标准检查及核心测试入口。
3. 先打通 C 核心加载与 ImGui 显示，再接入日志和双语基础界面。
4. 按总体设计实现渐进、预读、预算及超大图处理。
5. 主线完成后再评估更新检测排期；后续采用 cpp-httplib，届时明确版本信息协议、TLS 配置和网络测试。当前不以实现更新模块作为首版验收条件。

依赖来源、SDL3 / OpenGL 后端及默认鸿蒙字体已确定，四个 submodule 已完成集成。剩余重点是解码库和 C 引擎；字体 / IME / 跨屏 DPI 还需更完整验收。更新检测专用的 cpp-httplib 版本、TLS 后端和版本信息协议延后决定。
